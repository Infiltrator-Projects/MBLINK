# ELM327 Engine

The portable C ELM327 layer owns command framing, response parsing, adapter initialisation, capability probing, one-command-at-a-time session state and the formatted CAN diagnostic-channel contract used by ELM/Vgate-style text adapters. It is independent of BLE and does not contain OBD-II formulas, UDS service semantics or Mercedes-Benz addresses.

## Initialisation

```text
ATZ
ATE0
ATL0
ATS0
ATH0
ATSP0
ATI
```

Configuration stages require `OK`; reset/identity stages may return text. The final `ATI` response is retained as adapter identity.

## Parser contract

Transport input may be fragmented arbitrarily. `mblink_elm327_parser_feed()` accumulates bytes until the `>` prompt and reports exactly how many bytes it consumed. Bytes after the prompt remain the caller's responsibility.

Normalisation removes command echo and line-ending noise while retaining payload lines. Recognised adapter conditions include `NO DATA`, `STOPPED`, `UNABLE TO CONNECT`, bus-init errors, `CAN ERROR`, `BUFFER FULL`, `?` and `ERROR`. Prompt-only responses are malformed.

## Session contract

`MblinkElm327Session` binds the parser to `MblinkTransport` and allows one outstanding command. The caller supplies a monotonic millisecond clock and timeout.

Timeout, cancellation, transport-write failure, or unexpected non-whitespace bytes after a completed prompt require re-synchronisation before another command can start. This prevents late data from one request being mistaken for the next response. Trailing whitespace alone is harmless.

Callbacks are synchronous and observational: a callback may inspect the session but may not start another command re-entrantly. Access to one session instance must be serialized.

`mblink_elm327_session_init()` installs the transport receiver. `mblink_elm327_session_disconnect()` detaches it and reconnect reinstalls it. `mblink_elm327_session_deinit()` is final teardown and must be called after any synchronous event callback returns, before session/provider storage is destroyed.

## Capability probe

After initialisation the probe state machine may use:

```text
AT@1
ATDP
ATDPN
```

`AT@1` is optional. `ATDP` and `ATDPN` capture the active protocol description/number. Automatic-prefix responses such as `A6` are distinguished from the single hexadecimal protocol identifier `A`.

## ELM-managed ISO 15765 CAN channel

`mblink/elm327_can.h` is the text-adapter path for hardware that performs ISO-TP framing and flow control internally. It deliberately does **not** include or call `mblink/isotp.h`.

A caller supplies one physical diagnostic endpoint as either 11-bit or 29-bit TX/RX CAN identifiers. MBLINK validates identifier width but does not infer Mercedes-Benz addresses. The configuration state machine generates, in order:

```text
ATSH...   transmit CAN header
ATCRA...  receive CAN-address filter
ATCAF1    CAN automatic formatting on
ATCFC1    automatic ISO-15765 flow control on
```

Every stage requires a parsed `OK`. The established `MblinkElm327Session` executes those commands, so channel setup does not introduce another transport runner, timeout model or parser.

`mblink_elm327_can_build_pdu_command()` renders one complete diagnostic PDU as uppercase hexadecimal text and does not add ISO-TP PCI bytes. `mblink_elm327_can_decode_pdu()` converts ELM auto-formatted output back into one complete PDU. It accepts both single-line hex payloads and indexed multi-line output (`0:`, `1:` and so on), validating indexed sequence and an optional three-hex-digit declared message length before copying to caller storage.

The current request contract is intentionally bounded to 31 PDU bytes because the existing ELM session accepts commands shorter than 64 characters. Read-oriented UDS requests such as DiagnosticSessionControl, TesterPresent and a single ReadDataByIdentifier request fit within that limit. A larger request contract must be an explicit future change rather than silently bypassing session bounds.

## Two ISO-TP paths, one UDS layer

MBLINK intentionally has two ways to obtain the complete PDU consumed by UDS:

```text
BLE / ELM-compatible adapter
    -> ELM text session
    -> adapter-managed ISO 15765 formatting/flow control
    -> complete PDU
    -> UDS

raw CAN provider (future Linux SocketCAN, etc.)
    -> MBLINK Classical-CAN ISO-TP engine
    -> complete PDU
    -> UDS
```

This avoids double segmentation. Swift, Objective-C and Mercedes definition code do not decide how ISO-TP frames are transported.

## BLE probe boundary

The Apple provider may discover multiple writable/notify GATT characteristic pairs. Rather than trusting UUID shape alone, it enables notifications and sends an `ATI` probe generated and parsed by this C layer. Only a channel that produces a valid ELM response is promoted to the application transport.

CoreBluetooth owns GATT lifecycle and write sizing. It does not parse diagnostic payloads.

## Adapter portability

Vgate iCar Pro BLE 4.0 is the first validation target, not a hard-coded dependency. UUIDs, write modes and adapter quirks remain provider/profile concerns. The C ELM parser/session/CAN-channel contracts are adapter-neutral.
